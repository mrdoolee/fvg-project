# Flashcard Voice Game — GAS → 표준 웹앱 전환 브리핑

이 문서는 Google Apps Script(GAS) + 스프레드시트로 완성되어 실사용 검증까지 끝난
"Flashcard Voice Game"을, **여러 선생님이 각자 데이터로 쓸 수 있는 표준 웹앱**으로
전환하기 위한 인수인계 문서입니다. 아래 내용을 전제로 작업을 시작해주세요.

---

## 0. 절대 원칙

- **`mic-page`의 핵심 로직(음성인식 엔진 관리, 판정 로직)은 이미 수많은 실사용 버그를
  잡아서 안정화된 코드입니다. 이유 없이 재작성하지 말고 최대한 그대로 이식하세요.**
  아래 "6. 이미 해결된 버그 (재도입 금지)" 섹션이 특히 중요합니다.
- 시트 스키마(탭 이름, 열 순서, 헤더)는 **동결**되어 있습니다. 바꾸려면 먼저 사용자에게
  이유를 설명하고 승인을 받으세요.
- 진행 중 설계가 갈리는 지점이 생기면, 추측해서 진행하지 말고 사용자에게 질문하세요
  (특히 "5. 아직 결정 안 된 것" 항목).

---

## 1. 이 앱은 무엇인가

학생이 화면에 나온 단어/문장을 **소리 내어 말하면**, 마이크가 자동으로 듣고 정답 여부를
판정하는 발음 평가 웹앱. 결과는 시트에 자동 기록되고, "시간측정 모드"에서는 같은
단원·문항수로 응시한 기록 중 TOP 3 시간을 보여준다.

**사용자 두 종류**
- **교사(설치자)**: 로그인 후 본인 소유의 구글시트를 선택/생성해서 학생명부·문항을 관리
- **학생(최종 사용자)**: 로그인 없이 링크 접속 → 이름 선택 → 응시 (구글 계정 불필요)

---

## 2. 목표 아키텍처

```
[교사 브라우저]
  → 웹앱(Next.js, Vercel 배포) 접속 → 구글 로그인(OAuth, drive.file 스코프)
  → Google Picker로 본인 시트 선택 또는 신규 생성
  → 이후 이 웹앱이 Sheets API로 그 시트를 읽고 씀

[학생 브라우저]
  → 교사가 공유한 링크 접속 (로그인 불필요)
  → 이름 선택(학년→반→이름) → 문항 수신 → [마이크 시작] → 팝업으로 mic-page 오픈
  → mic-page(정적 HTML/JS, 지금 파일 거의 그대로 재사용)에서 실제 음성 인식·채점
  → 결과를 postMessage로 부모 창에 전달 → 부모 창이 API로 서버에 저장(Sheets API write)
```

- **호스팅**: GitHub 저장소 → Vercel 배포 (같은 계정으로 기존 CRA Sociogram 배포 경험 있음)
- **프레임워크**: Next.js 권장 (프론트엔드 + API 라우트를 한 프로젝트에서 관리 — GAS의
  "화면+서버로직 한 곳" 구조와 가장 가까움)
- **데이터 저장소**: 전용 DB(Firebase/Supabase 등) **사용하지 않음**. 계속 구글시트를 씀.
  이유: 전용 DB를 쓰면 제작자가 여러 학교 학생 데이터를 실제로 보관/운영하는 "관리자"가
  되어 개인정보·비용 책임이 제작자에게 넘어감. 구글시트 유지 시 데이터는 각 교사의
  구글 드라이브에만 존재하고 제작자 서버는 아무 데이터도 보관하지 않음 — 지금 앱 정보창의
  "제작자는 이 데이터에 접근하지 않습니다" 문구가 그대로 유지됨.
- **인증/권한**: 구글 OAuth + **`drive.file` 스코프** (전체 `spreadsheets` 스코프 아님)
  + Google Picker API. 이 조합은 별도 프로젝트(교외 출결관리 시스템)에서 이미 검증 완료:
  Sheets API 읽기/쓰기/시트추가/서식지정까지 전부 정상 동작 확인됨.
  **`drive.file`은 "비민감 권한"으로 분류되어 구글의 앱 검증 심사, 테스트 사용자 100명
  상한, "확인되지 않은 앱" 경고 화면이 전부 필요 없음.** 반드시 이 스코프를 쓸 것 —
  `spreadsheets` 스코프로 잘못 요청하면 심사·상한 문제가 재발함.
- **동시 쓰기 제어**: GAS의 `LockService` 역할을 대체해야 함. Sheets API의
  `values.append`는 자체적으로 다음 빈 행에 안전하게 추가하므로 명시적 락이 불필요할 가능성이
  높음 — 실제 동시 요청 테스트로 확인 필요 (28명 동시 제출 시나리오 기준).

## 3. 현재 파일 구성과 재사용 여부

| 파일 | 현재 역할 | 전환 시 |
|---|---|---|
| `gas-app/Code.gs` | 시트 CRUD, 인증 없는 세션 관리, LockService | **재작성** → Next.js API 라우트 (Sheets API 호출) |
| `gas-app/Index.html` | 학생 화면 뼈대 (GAS 템플릿 문법 `<?!= ?>` 사용) | **재작성** → React 컴포넌트. 디자인 토큰(CSS 변수)은 그대로 이식 가능 |
| `gas-app/Stylesheet.html` | 디자인 (CSS 변수 기반 토큰 시스템) | **거의 그대로 이식** — `<style>` 내용물을 그대로 옮기면 됨 |
| `gas-app/JavaScript.html` | `google.script.run` 호출, 팝업 통신, 상태관리 | **재작성 필요하나 로직은 그대로** — `google.script.run(...)` → `fetch('/api/...')` 로만 교체. 상태 관리 로직(드롭다운 캐스케이딩, 리더보드 렌더링, resetApp 등)은 그대로 이식 |
| `mic-page/index.html` | 마이크·음성인식·채점·파형·효과음 (순수 클라이언트 JS, GitHub Pages 정적 호스팅) | **거의 그대로 재사용.** 프레임워크와 완전히 무관한 순수 HTML/JS라 그대로 새 저장소에 옮겨도 됨. postMessage로 부모 창과 통신하는 구조라 부모가 GAS 페이지든 Next.js 페이지든 상관없음 |

첨부된 4개 파일(`Code.gs`, `Index.html`, `Stylesheet.html`, `JavaScript.html`, `mic-page/index.html`)을
Claude Code 세션에 함께 전달할 예정이니, 재작성 시 반드시 참고해서 **기능 누락 없이** 이식할 것.

## 4. 현재 시트 스키마 (동결 — 그대로 유지)

### `환경설정` (key-value)
| key | 용도 | 필수 |
|---|---|---|
| MIC_PAGE_URL | mic-page 배포 주소 | ★ |
| MIC_PAGE_ORIGIN | mic-page 도메인(postMessage origin 검증용) | ★ |
| BRAND_TEXT | 상단 브랜드 문구 | 선택 |
| APP_TITLE | 카드 제목·탭 제목 | 선택 |
| APP_SUBTITLE | 카드 부제 | 선택 |

### `학생명부`
`학년 | 반 | id(학번) | name(이름)` — 학생 화면에서 학년→반→이름 3단 드롭다운으로 좁혀 선택

### `데이터`
`question | answers | timeLimit | unit | lang`
- `answers`: 쉼표로 여러 정답 구분
- `timeLimit`: 초 단위, 비우면 5초 (채점 모드 전용)
- `unit`: 단원명, 전부 비어있으면 단원 선택 UI 자체가 안 뜸
- `lang`: 인식 언어 코드(`ko-KR`/`en-US` 등), 비우면 `ko-KR`
- `question` 셀 안 줄바꿈(Alt+Enter)은 화면에 그대로 반영됨 (`white-space: pre-line` 필요)

### `기록`
`일시 | 학번 | 이름 | 모드 | 점수 | 맞은문항수 | 틀린문항수 | 출제문항수 | 틀린문제들 | 소요시간(초) | 단원`
- 열 순서 고정 — 리더보드 계산이 위치 인덱스로 값을 읽음
- 시간측정 모드: 점수 관련 칸은 비워두고 소요시간만 채움
- 채점 모드: 소요시간 칸을 비워둠

## 5. 아직 결정 안 된 것 (Claude Code가 사용자에게 물어봐야 함)

- 교사가 처음 로그인했을 때: 빈 템플릿 시트를 자동 생성해줄지, 기존 시트를 Picker로
  고르게만 할지, 아니면 두 옵션 다 제공할지
- mic-page를 프로젝트마다(교사마다) 따로 배포하게 할지, 하나의 공용 정적 페이지를
  모두가 같이 쓰게 할지 (지금 GAS 버전은 "당분간은 공용, 확산되면 각자"로 결정했었음)
- `LockService` 대체가 정말 필요 없는지 실측 필요 — 필요하다면 어떤 방식으로 구현할지
  (예: Vercel의 서버리스 환경에서는 in-memory 락이 인스턴스 간 공유되지 않으므로,
  필요시 별도 조율 메커니즘 검토)
- 교사용 "정보/버전 안내" UI를 앱 내 어디에 둘지 (지금은 스프레드시트 상단 메뉴였는데,
  웹앱에서는 그 자리가 없어짐 — 헤더의 정보 아이콘 등으로 대체 필요)

## 6. 이미 해결된 버그 (재도입 금지)

`mic-page`를 재작성하지 말고 그대로 이식하라고 한 이유가 이것들입니다. 혹시 리팩터링하게
되더라도 아래 동작은 반드시 유지해야 합니다.

1. **GAS iframe 샌드박스가 마이크를 차단** → mic-page를 별도 정적 페이지로 완전히 분리한
   이유. 전환 후에도 음성인식이 필요한 화면은 반드시 최상위 브라우징 컨텍스트(팝업 등)에서
   실행되어야 함 — 임베드된 iframe 안에서 직접 돌리지 말 것.

2. **파형 시각화용 별도 `getUserMedia` 스트림이 SpeechRecognition의 오디오 캡처를 막음**
   → 해결: 별도 마이크 스트림을 쓰지 않고, `SpeechRecognition` 자신의 `onsoundstart`/
   `onsoundend` 이벤트로 파형 애니메이션을 구동. **마이크 소비자는 반드시 1개로 유지.**

3. **음성인식 엔진을 매번 `new SpeechRecognition()`으로 새로 만들면 마이크가 완전히
   죽는 경우 있음** (특히 재시동/자동복구 시) → 해결: **세션당 엔진 인스턴스 1개만 만들어
   재사용.** 재시동이 필요하면 `stop()` 후 약간의 지연(300ms) 뒤 같은 인스턴스에
   `start()`만 호출. 새 인스턴스를 만드는 코드 경로를 다시 추가하지 말 것.

4. **`recognition.continuous = true` + `evt.resultIndex` 기반 결과 처리** — continuous
   모드에서는 `evt.results`가 세션 누적 배열이므로, 매번 `evt.resultIndex`부터 새 결과만
   읽어야 함. `evt.results[0]`만 보면 두 번째 발화부터 오작동함.

5. **엔진이 `onend` 신호도 없이 조용히 멈추는 경우 대비 감시(watchdog) 타이머** —
   4초간 무반응 시 엔진을 stop→재start. 이 감시 로직 유지 필요.

6. **정답 판정**: 공백/문장부호 제거(`replace(/[^\p{L}\p{N}]/gu, '')`) + 발화 전체 일치
   또는 발화 내 개별 단어 일치(`isAnswerMatch`, 반복 발화 "수소 수소 수소" 허용) 두 가지
   경로 모두 유지.

7. **`location.reload()`는 쓰지 말 것** — 임베드/샌드박스 환경에서 빈 화면을 유발한 이력
   있음. 화면 전환은 페이지 이동 없이 상태 리셋으로 처리.

8. **팝업 차단 대응**: `window.open()`은 반드시 사용자 클릭 이벤트 핸들러 내부에서
   동기적으로 호출. 비동기 처리 후 열면 브라우저가 차단함.

9. **postMessage 보안**: 수신 시 반드시 `evt.origin` 검증. 부모→팝업 최초 메시지는
   origin을 모르므로 `'*'`로 보내되, 팝업이 응답하는 시점에 `evt.origin`을 신뢰 출처로
   고정해서 이후 계속 검증.

10. **비-구글 크로미움 브라우저(네이버 웨일, 오페라, 브레이브 등) 미지원** — Web Speech
    API의 실제 인식 서버는 구글이 정식 크롬에만 내장한 비공개 서비스라, 이런 브라우저는
    권한은 뜨지만 인식이 항상 실패함. 사용자 안내 문구로 "Chrome/Safari 사용" 명시 필요
    (코드로 해결 불가능한 브라우저 자체의 한계).
    - **(Next.js 이식 후 실측 추가)** 마이크로소프트 엣지는 완전히 실패하진 않지만
      자체 음성인식 서버(구글이 아님)를 써서 한글 인식률이 크롬보다 눈에 띄게 떨어짐 —
      `onresult`/`onerror: network`는 정상적으로 오가는데 인식된 텍스트 자체가 부정확한
      경우가 많음. 웨일처럼 "항상 실패"는 아니고 "품질이 나쁨"에 가까운 별개 증상이라
      안내 문구에 따로 구분해서 적어둠.

11. **iOS는 별도 브라우저 앱이어도 전부 WebKit 엔진** — Chrome for iOS를 깔아도 Safari와
    동일한 인식 성능. iOS 관련 테스트는 아직 미완료 상태로 남아있음.

## 7. 참고 — 그대로 유지해야 하는 UX 규칙

- 채점 모드: 문항별 제한시간 내 정답 필요, 시간초과 시 정답 공개 후 다음 문항
- 시간측정 모드: 제한시간 없이 맞을 때까지 대기, 맞으면 즉시 다음 카드
- 정답 시 "딩동"(고음→저음), 오답/시간초과 시 "땡"(저음 버저) — Web Audio API로 코드
  생성한 소리, 외부 음원 파일 없음. 반드시 사용자 제스처(버튼 클릭) 안에서 AudioContext
  생성/resume해야 모바일에서 소리가 막히지 않음
- 문항 글자 수에 따라 폰트 크기 자동 축소 (긴 속담·문장 대응)
- 리더보드는 **이름을 표시하지 않고 순위/시간만** 표시 (개인정보 노출 방지)
- 리더보드는 "같은 단원 + 같은 문항 수" 조건이 모두 일치하는 기록끼리만 비교
