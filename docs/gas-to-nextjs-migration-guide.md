# GAS → Next.js 마이그레이션 가이드

Google Apps Script(GAS) 컨테이너 바인딩 앱(스프레드시트/문서에 붙어 스크립트 편집기에서 배포하는 형태)을, 여러 사용자가 각자 자기 데이터로 쓸 수 있는 표준 웹앱(Next.js + Vercel)으로 옮길 때 쓰는 절차와 개념 매핑 정리. Flashcard Voice Game 프로젝트(`docs/handoff/`)를 실제로 이 방식으로 옮기면서 정리한 내용이다.

## 언제 이 가이드가 맞는 상황인가

- 원본이 **컨테이너 바인딩 GAS**(스프레드시트/문서에 스크립트가 붙어있고, `SpreadsheetApp.getActiveSpreadsheet()`처럼 "지금 이 파일"을 암묵적으로 참조하는 구조)
- 최종 사용자가 **여러 명(교사/관리자 등 "소유자" 역할)** 있고, 각자 자기 소유의 시트/문서로 독립적으로 써야 함 (1교사 1배포였던 GAS 구조를 다인원 공용 웹앱으로 확장)
- 데이터 저장소를 **계속 구글시트로 유지**하고 싶은 경우 (전용 DB 도입은 별개 판단 — 아래 "왜 DB를 안 썼는가" 참고)

## 0. 시작 전에 반드시 할 일

1. **원본 GAS 코드 전체와 실사용 검증 이력을 확보한다.** 코드만 보고 재작성하면 실사용 중 발견된 버그 수정들을 놓친다 — 특히 UI 쪽(마이크/카메라 등 브라우저 API를 쓰는 화면)은 "왜 이렇게 짰는지" 이유가 주석 하나 없이 코드 구조에만 녹아있는 경우가 많다. 가능하면 원작자에게 "이 부분 왜 이렇게 했어요?"를 물어볼 기회를 만든다.
2. **원본을 그대로 diff 비교 가능한 위치에 보존한다** (이 프로젝트에선 `docs/handoff/current-code/`). 나중에 "이 동작이 원래도 이랬나?"를 검증할 유일한 방법이다.
3. **스키마(시트 탭 이름, 열 순서, 헤더)를 동결 대상으로 선언한다.** 열 순서를 인덱스로 읽는 코드가 반드시 있고(`data[i][3]` 같은), 재작성 중 무심코 순서를 바꾸면 그 시점부터 조용히 깨진다.

## 1. 개념 매핑

| GAS | Next.js 등가물 | 비고 |
|---|---|---|
| `doGet()` / `doPost()` | App Router 페이지(`page.tsx`) / API 라우트(`route.ts`) | GAS는 요청 하나에 화면+로직이 한 함수였는데, Next.js에선 페이지(화면)와 API 라우트(로직)가 분리됨 |
| `HtmlService.createTemplateFromFile()` + `<?!= ?>` 템플릿 | React 컴포넌트 + props/fetch | 서버가 값을 미리 주입해서 HTML을 만들던 방식 → 클라이언트가 API를 fetch해서 상태로 들고 렌더링하는 방식으로 전환 |
| `google.script.run.foo()` | `fetch('/api/foo')` | 로직은 그대로 두고 호출부만 REST fetch로 교체 가능한 경우가 많음 (아래 "그대로 옮길 수 있는 부분" 참고) |
| `SpreadsheetApp.getActiveSpreadsheet()` | Sheets API REST 호출 (`spreadsheetId`를 매번 명시) | 컨테이너 바인딩의 "암묵적으로 이 파일"이 사라지므로, 어떤 시트인지 매 요청마다 어디선가 알아내야 함 — 인증/세션 설계의 핵심 문제가 됨 |
| `PropertiesService` / 스크립트 속성 | 환경변수 (`.env.local`, Vercel Environment Variables) | 원본이 "환경설정 탭"처럼 시트 자체에 설정을 뒀다면, 그 패턴을 유지할지 env로 옮길지 판단 필요 (아래 참고) |
| `LockService` | 없음 — Sheets API의 `values.append`가 자체적으로 다음 빈 행에 안전하게 씀 | 실측 없이 "당연히 락이 필요하다"고 가정하지 말 것 (아래 "동시성" 참고) |
| `Session.getActiveUser()` / 이메일 인증 | OAuth (아래 3장) | GAS는 구글 워크스페이스 내부에서 로그인 상태가 이미 보장되지만, 일반 웹앱은 처음부터 인증을 설계해야 함 |
| Apps Script 배포(웹앱 URL) | Vercel 배포 | 1인 1배포 구조였다면, 웹앱 전환 시 "배포도 1인 1개"를 유지할지 "공용 배포 하나로 다인원"을 할지부터 정해야 함 — 대개 후자가 목적임 |

## 2. 그대로 옮길 수 있는 부분과 재작성해야 하는 부분

- **순수 클라이언트 JS(브라우저 API를 직접 다루는 코드)는 재작성하지 말고 그대로 이식한다.** 음성인식, 카메라, 파일 업로드 진행률처럼 브라우저 API를 직접 건드리는 코드는 프레임워크와 무관하게 동작하므로, `public/` 폴더에 정적 파일로 그대로 복사해 넣는 게 제일 안전하다. 리팩터링하고 싶은 유혹이 들어도 참는다 — 실사용 버그 수정이 코드 구조 안에 녹아있어서, "정리"하다가 그 수정을 놓치기 쉽다.
- **상태관리/로직(드롭다운 캐스케이딩, 폼 검증, 렌더링 순서 등)은 로직 자체는 그대로 두고 `google.script.run` 호출부만 `fetch`로 교체한다.** 통째로 새로 설계하지 않는다 — 이미 실사용 검증된 흐름이면 그 흐름을 존중한다.
- **서버 로직(`Code.gs`의 함수들)은 API 라우트로 1:1 매핑하며 재작성한다.** 열 인덱스 읽기 로직, 검증 로직은 그대로 포팅하되, `SpreadsheetApp` 호출부만 Sheets API REST 호출로 바꾼다.

## 3. 인증 설계 — 가장 많이 틀리는 부분

컨테이너 바인딩 GAS는 "이 스크립트 = 이 시트"라 인증 문제가 아예 없었다. 웹앱으로 옮기면 **"어떤 요청이 어떤 사용자의 어떤 시트에 접근하는가"**를 처음부터 설계해야 한다. 사용자군이 두 종류로 나뉘는 경우(예: "소유자"와 "익명 최종 사용자")가 특히 까다롭다.

### 3.1 스코프는 최소로

Google Sheets/Drive API를 쓸 때 `https://www.googleapis.com/auth/spreadsheets`(전체 스코프) 대신 **`https://www.googleapis.com/auth/drive.file`**(그 앱이 만들었거나 Picker로 사용자가 직접 연 파일에만 접근)을 쓸 수 있는지 먼저 검토한다. `drive.file`은 "비민감 스코프"로 분류돼서:
- 구글의 앱 검증(verification) 심사가 필요 없다
- 테스트 사용자 100명 상한이 없다 ("확인되지 않은 앱" 경고 화면도 없음)
- OAuth 동의 화면을 곧바로 "프로덕션" 게시 상태로 전환할 수 있다 (전환 안 하고 "테스트" 상태로 두면 refresh_token이 7일 만에 만료되는 함정이 있음 — 반드시 프로덕션 전환할 것)

`drive.file`은 Sheets API의 읽기/쓰기/시트추가/서식지정까지 전부 지원한다. "혹시 스코프가 부족해서 안 될까봐" 미리 넓은 스코프를 쓰지 않는다.

### 3.2 소유자(로그인 사용자) 쪽 흐름

표준 OAuth 2.0 authorization code flow:
1. `/api/auth/google` — 로그인 버튼 클릭 시 CSRF 방지용 `state` 랜덤값을 쿠키에 저장하고 구글 동의 화면으로 리다이렉트 (`access_type=offline`, `prompt=consent`로 매번 요청 — refresh_token을 확실히 받기 위해 필수)
2. `/api/auth/google/callback` — `code`를 `refresh_token`으로 교환, 이 시점 세션을 httpOnly 쿠키에 암호화해서 저장 (아래 3.4)
3. Picker/시트 생성 등 이후 흐름은 쿠키의 `refresh_token`으로 그때그때 `access_token`을 새로 발급받아 사용

### 3.3 익명 최종 사용자 쪽 흐름 — 진짜 어려운 부분

원본 GAS가 "소유자만 로그인, 최종 사용자는 로그인 없이 이름만 선택" 같은 구조였다면(교육용 도구에서 흔함), 이 비대칭을 웹앱에서도 유지해야 한다. 문제는: **익명 사용자의 요청을 서버가 대신 처리하려면 그 순간 "소유자"의 access_token이 있어야 하는데, 익명 사용자는 로그인을 안 했으니 그 토큰을 어디서 가져오나?**

세 가지 선택지와 트레이드오프:

| 방식 | 서버가 저장하는 것 | 장점 | 단점 |
|---|---|---|---|
| **A. 링크에 암호화해서 직접 담기** (권장 기본값) | 없음 | 서버가 정말 아무것도 안 들고 있음. 링크 하나 유출돼도 그 소유자의 그 파일만 노출(피해 범위 국소적) | 링크가 길다(암호화 블록). 재발급해도 기존 링크가 자동 무효화 안 됨 |
| B. 별도 DB/KV(Redis 등)에 매핑 저장 | 모든 소유자의 access-token 매핑을 서버가 보유 | 링크가 짧고 깔끔함, 세밀한 개별 회수 가능(이론상) | 서버가 사실상 "모든 사용자 데이터의 마스터 키 보관소"가 됨 — 암호화 키 하나가 뚫리면 전원 노출. TTL/정리 로직을 직접 관리해야 하고 안 하면 무한정 쌓임 |
| C. 소유자 본인 파일 안에 저장 (예: 설정 시트 탭) | 없음(파일 자체에 있음) | A와 동일하게 서버 무저장 | **순환 참조**: 그 파일을 읽으려면 이미 유효한 토큰이 있어야 하는데, 그 토큰이 바로 그 파일 안에 있음 → 단독으로는 성립 안 됨. A와 결합해서 "재발급 편의" 용도로만 의미 있음(소유자 본인이 로그인한 상태에서 자기 파일에 쓰고 읽는 건 순환 참조가 아님) |

**A를 기본값으로 추천한다.** 이유는 표 안의 장단점 이상으로, **애초에 전용 DB를 안 쓰기로 한 이유(아래 4장)와 정합성이 맞기 때문**이다. B는 "DB는 안 쓴다"고 해놓고 결국 access-token 저장소라는 DB의 변종을 다시 만드는 셈이라, 프로젝트의 원래 동기를 무력화한다. 이 판단은 한 번 뒤집혔다가 되돌린 적이 있다 — Redis로 바꿔봤다가, "서버가 아무것도 안 든다"는 핵심 가치와 "링크 하나 유출 = 그 반만 뚫림"이라는 피해 범위 국소화 둘 다 잃는다는 걸 뒤늦게 깨닫고 되돌렸다. C는 A의 보조 수단으로만 쓴다(예: 소유자가 재방문 시 "예전에 만든 링크를 그대로 보여주기" — 이건 소유자 본인의 살아있는 세션으로 읽고 쓰니 순환 참조가 아니다).

A를 구현할 때:
```
링크 = /무언가?token=AES-256-GCM암호화({ 리소스ID, refresh_token })
```
익명 요청마다: `token` 복호화 → 그 안의 `refresh_token`으로 `access_token` 새로 발급 → API 호출 → **아무것도 저장하지 않고 응답만 반환**. 암호화 키(예: `LINK_SECRET_KEY`)는 서버 환경변수로만 존재하고 절대 커밋하지 않는다.

### 3.4 소유자 세션도 최소한으로

소유자용 세션 쿠키도 "설정 흐름 동안만 쓰는 짧은 토큰"으로 설계한다(예: 1시간). 장기 계정 시스템을 새로 만들 필요 없다 — 소유자는 필요할 때마다 다시 로그인하면 그만이고, 어차피 로그인 흐름 자체가 가볍다.

## 4. 왜 DB를 새로 안 쓰는가 (도입 전에 한 번은 따져볼 질문)

컨테이너 바인딩 GAS는 데이터가 각 소유자의 구글 드라이브에 있었다 — 원작자(개발자)는 그 데이터를 한 번도 실제로 보유한 적이 없다. 웹앱으로 옮기면서 전용 DB(Firebase/Supabase/Postgres 등)를 도입하면, 이 성질이 깨진다: 이제 개발자가 여러 사용자의 데이터를 실제로 보관/운영하는 "관리자"가 되고, 그에 따르는 법적/개인정보 책임(특히 미성년자 데이터가 걸린 경우)을 새로 지게 된다.

계속 구글시트를 데이터 저장소로 쓰면:
- 데이터는 각 소유자의 드라이브에만 존재
- 개발자 서버는 요청 처리 순간에만 잠깐 접근하고 아무것도 남기지 않음
- "이 앱은 여러분의 데이터에 접근하지 않습니다"라는 문구를 실제로 지킬 수 있음

이 판단이 안 맞는 경우도 있다 — 사용자 수가 아주 많아지거나, 시트 API의 속도/쿼터 한계에 걸리거나, 복잡한 관계형 쿼리가 필요해지면 DB가 답일 수 있다. 다만 "그냥 편해서" 도입하지 말고, 이 트레이드오프를 사용자에게 명시적으로 설명하고 동의를 받은 뒤 결정한다.

## 5. Sheets API를 직접 REST로 쓸지, `googleapis` SDK를 쓸지

무거운 `googleapis` 패키지 대신 `fetch`로 Sheets API v4를 직접 감싸는 얇은 래퍼를 추천한다:

- `values.get` — 탭 전체 읽기 (GAS의 `getDataRange().getValues()}` 대응)
- `values.append` — 다음 빈 행에 안전하게 추가 (GAS의 `appendRow()` 대응, 동시 쓰기도 자체적으로 안전 — 5장 참고)
- `values.update` — 특정 범위를 그 자리에서 덮어쓰기 (append와 달리 새 행을 안 만듦 — "설정값 하나만 갱신" 같은 데 씀)
- `values.batchUpdate` — 여러 범위를 한 번에 씀 (템플릿 초기화용)
- `spreadsheets.create` — 새 스프레드시트를 탭 구조까지 갖춰서 생성

탭 이름이 없을 때(404류 응답)를 "정상적으로 있을 수 있는 상황"으로 처리해서 null을 반환하게 만들어두면, 상위 로직에서 "이 탭이 없다"는 사용자向 에러 메시지를 자연스럽게 만들 수 있다.

## 6. 동시성 — 락이 정말 필요한지 실측하기

GAS의 `LockService`가 있던 자리를 보고 "그럼 여기도 락이 필요하겠구나"라고 바로 넘겨짚지 않는다. Sheets API의 `values.append`는 자체적으로 동시 요청을 다음 빈 행에 안전하게 분배하도록 설계되어 있다 — **가정하지 말고 실측한다.** 방법: 같은 스프레드시트에 짧은 시간 안에 N개(원본 GAS 규모에 맞는 동시 사용자 수)의 동시 append 요청을 쏘고, 응답 성공률과 실제로 시트에 몇 행이 들어갔는지(중복/누락 없는지)를 직접 확인한다. 락 없이 통과하면 그대로 가고, 실패율이 보이면 그때 조율 메커니즘(큐, 재시도, 서버리스 환경이라 인메모리 락은 인스턴스 간 공유가 안 된다는 점 감안)을 설계한다.

## 7. 자주 걸리는 함정

- **OAuth 동의 화면을 "테스트" 상태로 방치** — `drive.file`처럼 비민감 스코프만 쓰면 검증 없이 "프로덕션"으로 바로 전환 가능한데, 안 하면 refresh_token이 7일 만에 죽는다.
- **`redirect_uri`/JS 원본을 로컬만 등록** — 배포 도메인(예: `https://foo.vercel.app`)을 Google Cloud Console의 OAuth 클라이언트에 추가로 등록 안 하면 `redirect_uri_mismatch`. 로컬/배포 둘 다 등록해두고 둘 다 유지한다.
- **Picker용 API 키에 실제 값 대신 placeholder가 들어간 채로 저장됨** — 배포 플랫폼의 환경변수 UI에서 폼에 남아있던 예시 텍스트(`https://api.example.com` 같은)를 안 지우고 저장 버튼을 눌러버리는 실수가 은근히 잦다. 저장 후 그 기능이 실제로 동작하는지(에러 메시지가 사라지는지)로 검증한다.
- **"Sensitive" 환경변수 UI가 저장 후에도 빈칸처럼 보임** — 일부 배포 플랫폼은 민감 변수를 저장한 뒤 편집 화면에 실제 값 대신 회색 placeholder를 보여준다. 화면이 비어 보인다고 저장이 안 됐다고 단정하지 말고, 그 값에 의존하는 기능이 실제로 동작하는지로 확인한다.
- **Picker API 키에 애플리케이션/HTTP 리퍼러 제한이 걸려있는데 배포 도메인이 허용 목록에 없음** — "API developer key is invalid" 에러로 나타난다. API 키의 애플리케이션 제한사항(HTTP 리퍼러)과 API 제한사항(허용 API 목록에 Picker API 포함 여부) 둘 다 확인.
- **환경설정류 탭을 빈 칸으로 템플릿 생성** — 새 사용자가 뭘 채워야 할지 모른다. 지우고 써도 되는 예시 값/행을 채워서 만들어주면 즉시 써볼 수 있고, 각 칸이 뭘 뜻하는지 문서 없이도 유추 가능해진다.
